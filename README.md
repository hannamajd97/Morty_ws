# voice_guided_grasping_code

Source code for the Voice-Guided Robotic Grasping System (UR3e + 3D-printed
gripper + GraspGen). ROS 2 workspace, GraspGen integration, trained models, and
helper / experiment scripts — everything needed to build and run the system on
a new machine.

## What is NOT included (regenerable / removed on purpose)

- `build/`, `install/`, `log/` — regenerated by `colcon build`.
- `__pycache__/`, `*.egg-info/`, `*.pyc` — Python caches.
- The full GraspGen **training dataset** (`grasp_dataset/`, large scene clouds)
  — not needed to run inference. Only the small `sample_data/` test clouds are kept.
- The `.morty_env` secrets file is **not shipped at all** (it would have held
  live LLM credentials). Create it yourself before running the voice layer
  — see "Run it" below for the template.

## First steps on a new machine

Full details: `docs/1_Installation.docx` (Ubuntu 22.04, ROS 2 Humble, NVIDIA GPU
≥ 12 GB, CUDA 12.8, PyTorch cu128, pip deps, GraspGen extras).

```bash
# place the workspace at ~/morty_ws (the default the scripts fall back to;
# any other location works when WS_DIR points at it)
git clone git@github.com:hannamajd97/Morty_ws.git ~/morty_ws
cd ~/morty_ws

# python deps
pip install --user -r requirements.txt

# build
source /opt/ros/humble/setup.bash
colcon build --symlink-install
source install/setup.bash
```

## Run it

Full details in `docs/2_Launches_and_First_Run.docx` and `docs/3_Fast_Run.docx`.

### 1. Create the `.morty_env` secrets file

This file is intentionally **not shipped** so no live API key leaks into the
submission. Create it yourself at `~/morty_ws/.morty_env`, paste in
your own keys, and lock the permissions so it is readable by you only:

```bash
nano ~/morty_ws/.morty_env     # create the file with the template below
chmod 600 ~/morty_ws/.morty_env
```

You only need credentials for the provider(s) you actually plan to use.
The other block can be left out entirely — the launcher only reads the
variables for the path you take.

#### Scenario A — OpenAI only (most common)

If you have only an OpenAI key, paste this into `.morty_env`:

```bash
# OpenAI direct (used by ./morty.sh without --debug)
export OPENAI_API_KEY_DIRECT="sk-..."           # <-- your key from platform.openai.com
export OPENAI_MODEL="gpt-5.4-mini"              # optional; this is the default
```

Then run the default launcher:

```bash
./morty.sh --fake          # simulated robot
./morty.sh                 # real UR3e
./morty.sh --voice-only    # chat + gripper, no grasping
```

`--debug` will refuse to start (no Bedrock key) — that is expected; just
omit `--debug`.

#### Scenario B — AWS Bedrock only (cheaper dev path)

If you have only an AWS Bedrock bearer token, paste this instead:

```bash
# AWS Bedrock (used by ./morty.sh --debug)
export AWS_BEARER_TOKEN_BEDROCK="ABSK..."       # <-- your Bedrock bearer token
export AWS_REGION="us-east-1"
export BEDROCK_MODEL="us.anthropic.claude-haiku-4-5-20251001-v1:0"
```

Then always pass `--debug` so the launcher picks the Bedrock path:

```bash
./morty.sh --debug --fake
./morty.sh --debug
./morty.sh --debug --voice-only
```

Plain `./morty.sh` (no `--debug`) will refuse to start because no
`OPENAI_API_KEY_DIRECT` is set — that is expected.

#### Scenario C — Both providers

If you have both, include both blocks and switch between them with the
`--debug` flag. The two providers do not interfere — each launcher only
reads the variables it actually needs.

### 2. Launch

See Scenario A / B above for the matching command, or:

```bash
./morty.sh --fake          # simulated robot
./morty.sh                 # real UR3e
./morty.sh --voice-only    # chat + gripper, no grasping
```

## Run experiments

```bash
bash ~/morty_ws/tools/run_grasp_experiment.sh --tag run1
# logs + structured CSV/JSON appear under src/experiment_logs/
# then:  python3 tools/aggregate_grasp_experiments.py  /  generate_experiment_plots.py  /  build_experiment_report.py
```

See `tools/README.md` for the full tool reference.

## Notes

- The scripts resolve the workspace from their own location and fall back
  to `~/morty_ws`; set `WS_DIR` to use another location.
- GraspGen runs **in-process** by default (no separate service). To use the
  standalone ZMQ service instead, run `./scripts/start_graspgen.sh` and
  `export GRASPGEN_MODE=zmq`.
- The GraspGen `.pth` weights under `GraspGen/models/` are NVIDIA's GraspGen
  checkpoints, included here for convenience so the system runs out of the box.
